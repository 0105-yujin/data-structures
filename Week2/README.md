# Week2: 알고리즘 복잡도와 Big-O

## 1. 실습 목표
- 입력 크기 n에 따른 실행 시간 변화를 코드로 확인
- O(1), O(n), O(n²)의 차이를 실제 실행 시간으로 체감
- 선형 탐색과 이분 탐색을 구현하고 성능 비교

## 2. 실습 내용
| 단계 | 내용 | 복잡도 |
|---|---|---|
| 1 | 첫 원소 접근 `data[0]` | O(1) |
| 2 | 전체 순회 카운트 | O(n) |
| 3 | 중첩 반복문 | O(n²) |
| 4 | 선형 탐색 `linear_search` | 최악 O(n) |
| 5 | 이분 탐색 `binary_search` | 최악 O(log n) |
| 6 | n = 10 ~ 1,000,000 실행 시간 측정, 표·그래프 | - |

## 3. 코드 설명
- **선형 탐색**: 처음부터 하나씩 비교하며 target의 인덱스를 반환하고, 없으면 -1을 반환합니다.
- **이분 탐색**: 정렬된 데이터에서 `mid`를 기준으로 탐색 범위를 절반씩 줄입니다. 정렬이 전제 조건입니다.
- **측정 방법**: `time.perf_counter()`로 최악의 경우(마지막 원소 탐색)를 측정했습니다.

## 4. 측정 결과 (n = 1,000,000)
| 탐색 | 실행 시간 |
|---|---|
| 선형 탐색 | 약 0.064초 |
| 이분 탐색 | 약 0.00002초 |

n이 커질수록 선형 탐색은 n에 비례해 증가했고, 이분 탐색은 거의 변하지 않았습니다.

## 5. 이론값과 측정값 비교
- 선형 탐색은 n이 10배가 될 때 시간도 대략 10배씩 늘어 O(n)과 일치했습니다.
- 이분 탐색은 연산 횟수가 log₂n(n=100만일 때 약 20회)이라 시간 증가가 매우 작았습니다.
- n=10 구간에서 선형 탐색이 비정상적으로 느린 것은 첫 실행 지연과 함수 호출 오버헤드 때문입니다.

## 6. 느낀 점
같은 탐색임에도 n이 100만일땐 선형 탐색이 약 0.064초, 이분 탐색은 약 0.00002초로 3000배 넘게 차이가 났다. 데이터가 많아질수록 알고리즘 선택이 성능을 좌우할 수 있다는 점을 숫자로 확인했다.
